## 0. 작업 순서 한눈에

아래 순서대로 하면 서비스가 중단되지 않는다. **순서를 바꾸면 앱이 깨진다.**

```
[1단계] 서버 — 환경변수만 변경               재배포 불필요
          ALGO_K=3 → 2

[2단계] 서버 — 코드 변경 후 배포             앱 수정 불필요
          군구 좌표 판정 추가
          인천 외 좌표 가드 추가
          응답에 k2_hotspots 추가 (k3_hotspots도 그대로 둔다)

[3단계] 앱 — 코드 변경 후 배포
          k3_hotspots → k2_hotspots 로 읽는 키 변경
          400 응답 처리 추가

[4단계] 서버 — 앱 배포 확인 후
          k3_hotspots 제거 후 재배포
```

2단계에서 응답 필드를 **두 개 다 내려주는 것**이 핵심이다. 그래야 구버전 앱과 신버전 앱이 동시에 동작한다. K3s 컨테이너 전환 때 기존 서버를 켜둔 채 새 포트로 병행 검증했던 것과 같은 방식이다.

급하지 않다면 1단계와 2단계만 먼저 하고, 3·4단계는 다른 앱 수정 사항과 묶어서 한 번에 배포해도 된다.

## 2. S-1 — `ALGO_K` 를 2로

### 왜

v6 검증에서 경유 핫스팟 개수 K별 회피 성능을 측정한 결과 K=2가 최선이었다.

| K | hard case | 통과 완전 제거 | 원본 대비 악화 |
| --- | --- | --- | --- |
| **2** | **75.0%** | **12건** | **2건** |
| 3 | 80.2% | 9건 | 3건 |
| 4 | 83.3% | 6건 | 5건 |

### 어떻게

서버 `.env` 파일에서 한 줄만 고친다.

```
ALGO_K=2
```

알고리즘 파라미터는 코드 상수가 아니라 환경변수로 분리되어 있으므로 **코드 수정과 재배포가 필요 없다.** 컨테이너 재시작만 하면 된다.

### 확인

`POST /route/recommend` 를 한 번 호출해서 응답의 핫스팟 배열 길이가 2인지 본다.

## 3. S-2 — 출발지 좌표로 군구 판정

### 왜

서버에는 군구 필터 코드가 살아 있지만, 앱이 `district` 값을 보내지 않아 항상 폴백이 발동한다. 그래서 인천 전체 핫스팟 1,535곳이 대상이 되고 있다(코드 조사 `F-12`).

이 상태는 v6에서 측정되었고, 필터를 적용한 v5보다 hard case가 9.4%p 높았다(75.0% vs 65.6%).

앱을 고치지 않고 서버만으로 필터를 되살리기 위해, **출발지에서 가장 가까운 CCTV 핫스팟의 소속 군구**를 그 요청의 군구로 삼는다. v9 검증에서 이 방식의 정확도는 90.4%로, 기존 표본 라벨(81.7%)보다 높았다.

> **참고.** 2026년 7월 1일 인천시 행정체제가 개편되어 중구·동구가 제물포구·영종구로, 서구가 서해구·검단구로 바뀌었다. 핫스팟 데이터는 개편 전 이름을 쓰므로, 앱이 역지오코딩으로 얻은 현재 구 이름을 보내는 방식(방법 A)은 이름이 맞지 않아 쓸 수 없다. 본 방식은 핫스팟 데이터 안의 값만 사용하므로 개편의 영향을 받지 않는다.

### 위치 찾기

```bash
grep -rn "source_district" --include=*.py .
grep -rn "len(subset)" --include=*.py .
```

`algorithm.py` 의 460행 부근에 아래 형태의 코드가 있다.

```python
subset if len(subset) > 0 else hotspots
```

이 줄보다 **위쪽**, `subset` 을 만들기 직전에 분기를 넣는다.

### 무엇을 넣나

```python
# --- 추가: district가 없거나 알 수 없는 값이면 출발지 좌표로 판정한다 ---
# origin은 (lat, lon) 형태를 가정한다. 실제 변수명에 맞춰 조정할 것.

KNOWN_DISTRICTS = set(hotspots['source_district'].unique())

if district is None or district not in KNOWN_DISTRICTS:
    dists = haversine_vec(origin, HOTSPOT_COORDS)   # 아래 주석 참조
    district = hotspots.iloc[int(dists.argmin())]['source_district']

# --- 여기서부터는 기존 코드 ---
subset = hotspots[hotspots['source_district'] == district]
...
```

세 가지만 확인하면 된다.

**첫째, 벡터 거리 함수가 이미 있는가.** `algorithm.py` 는 노트북에서 이식된 것이라 `haversine` 계열 함수가 있을 것이다. 좌표 하나와 배열 전체의 거리를 한 번에 구하는 형태가 없으면 아래를 추가한다.

```python
import numpy as np, math

def haversine_vec(p, coords):
    """p(lat, lon) 와 coords(N,2) 배열 사이의 거리 (km)"""
    lat1, lon1 = math.radians(p[0]), math.radians(p[1])
    lat2 = np.radians(coords[:, 0])
    lon2 = np.radians(coords[:, 1])
    dlat, dlon = lat2 - lat1, lon2 - lon1
    a = np.sin(dlat/2)**2 + math.cos(lat1) * np.cos(lat2) * np.sin(dlon/2)**2
    return 6371.0 * 2 * np.arcsin(np.sqrt(a))
```

**둘째, 좌표 배열을 시작 시 한 번만 만든다.** 핫스팟과 회피 영역은 서버 시작 시 1회 로드하도록 되어 있으므로, 그 옆에 아래를 추가한다.

```python
# 핫스팟 로드 직후 (모듈 전역 또는 startup 이벤트)
HOTSPOT_COORDS = hotspots[['latitude', 'longitude']].values
```

**셋째, 기존 폴백은 그대로 둔다.** `subset if len(subset) > 0 else hotspots` 는 강화군처럼 후보가 드문 경우의 안전장치다.

### 덤으로 되살아나는 것

`district` 값이 채워지면 **강화군 Buffer 반경 2.5km 특례**도 자동으로 작동한다. 별도 수정이 필요 없다.

### 로그를 남긴다

코드 조사 D그룹(운영 관측 불가, 로깅 0건)을 조금이나마 메우기 위해, 판정 결과를 한 줄 남겨 둔다. 베타 로그로 이 방식의 정확도를 나중에 재검증할 수 있다.

```python
logger.info(
    "district_judged=%s origin=%.6f,%.6f nearest_km=%.3f",
    district, origin[0], origin[1], float(dists.min())
)
```

## 4. S-3 — 인천 외 좌표 거절 (4km 가드)

### 왜

S-2를 넣으면 인천 밖 좌표가 들어와도 오류가 나지 않고 엉뚱한 군구가 나온다. 서울에서 요청해도 인천 핫스팟을 경유하는 경로가 생성된다. 코드 조사 E그룹(`F-07`~`F-11`, 입력 검증 부재)에 해당한다.

v8 검증에서 인천 내부 표본 200쌍의 출발지-최근접 핫스팟 거리는 최대 2,895m였다. 여유를 두어 **4,000m**를 임계값으로 잡는다.

### 어떻게

S-2에서 구한 `dists.min()` 을 그대로 쓴다.

```python
if district is None or district not in KNOWN_DISTRICTS:
    dists = haversine_vec(origin, HOTSPOT_COORDS)
    nearest_km = float(dists.min())

    # --- 추가: 인천 외 지역 거절 ---
    if nearest_km > 4.0:
        raise HTTPException(
            status_code=400,
            detail="인천 지역 좌표가 아니다. 현재 인천광역시에서만 이용할 수 있다."
        )

    district = hotspots.iloc[int(dists.argmin())]['source_district']
```

임계값도 환경변수로 빼 두면 나중에 조정이 쉽다.

```
ALGO_MAX_ORIGIN_DIST_KM=4.0
```

### 주의

**앱이 현재 400 응답을 별도로 처리하지 않는다.** 지금은 502만 분기되어 있다. A-2에서 함께 처리한다. 앱 수정 전이라면 사용자에게 일반 오류 메시지가 뜨므로, 동작에는 문제가 없으나 안내가 부정확하다.

### 2단계 — 서버에 새 필드 추가 (구 필드 유지)

응답 모델에 필드를 하나 더 만든다. Pydantic 모델이라면 이런 형태다.

```python
class RouteResponse(BaseModel):
    ...
    k3_hotspots: list[HotspotOut]   # 유지. 4단계에서 제거한다
    k2_hotspots: list[HotspotOut]   # 추가
```

응답을 만드는 곳에서 같은 값을 두 필드에 넣는다.

```python
# 응답 조립부
selected_out = [...]                 # 기존에 k3_hotspots에 넣던 값

return RouteResponse(
    ...
    k3_hotspots=selected_out,        # 유지
    k2_hotspots=selected_out,        # 추가
)
```

이 상태로 배포하면 **구버전 앱은 그대로 동작하고**, 신버전 앱은 새 필드를 읽는다.

## 6. A-1 — 앱 응답 파싱 키 변경

### 위치 찾기

```bash
grep -rn "k3_hotspots\|k3Hotspots" --include=*.dart lib/
```

두 군데가 나올 것이다.

1. 응답 모델(DTO)의 `fromJson`
2. 그 값을 지도에 그리는 화면

### 무엇을 바꾸나

**JSON 키와 Dart 변수명은 별개다.** 최소 변경으로 가려면 `fromJson` 의 키 문자열만 바꾸면 된다.

```dart
// 응답 모델의 fromJson — 키 문자열만 변경
hotspots: (json['k2_hotspots'] as List<dynamic>? ?? [])   // 'k3_hotspots' 에서 변경
    .map((e) => HotspotDto.fromJson(e as Map<String, dynamic>))
    .toList(),
```

Dart 쪽 변수명까지 `k3Hotspots` 로 되어 있다면, 참조하는 곳을 모두 고쳐야 하므로 IDE의 이름 바꾸기(Rename Symbol) 기능을 쓰는 편이 안전하다. 이 기회에 `waypointHotspots` 처럼 숫자가 없는 이름으로 두는 것을 권한다.

### 안전장치

서버가 2단계 상태(두 필드 모두 반환)일 때 앱을 먼저 배포해도 되도록, 한동안 양쪽을 모두 받아들이게 해도 된다.

```dart
final rawList = json['k2_hotspots'] ?? json['k3_hotspots'] ?? [];
```

4단계가 끝나면 이 줄은 정리한다.

## 7. A-2 — 앱의 HTTP 400 처리

### 위치 찾기

```bash
grep -rn "502" --include=*.dart lib/
```

`route_repository.dart` 의 87~93행 부근에 502 분기가 있다. 그 옆에 400 분기를 추가한다.

### 무엇을 넣나

```dart
// 기존 502 분기 옆에 추가
if (response.statusCode == 400) {
  // 서버가 인천 외 지역 등 입력 문제를 알려준 경우
  throw RouteRequestException(
    _extractDetail(response.body) ?? '이 위치에서는 경로를 만들 수 없다',
  );
}
```

Presentation 계층에서 이 예외를 사용자 메시지로 노출한다. Riverpod `AsyncValue.when` 의 `error` 분기에서 처리하면 된다.
