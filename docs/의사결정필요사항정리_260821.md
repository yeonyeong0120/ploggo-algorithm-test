■ A. 선행 확인 필요 (다른 결정의 전제)

A-1. Tmap 보행자 경유지 개수 상한
  현황: 공식 문서에 상한 명시 없음. 일부 사례에서 5개 제한 보고.
  확인 방법: tmapWaypointLimitTest_260731.ipynb 실행 (12회 호출, 20초)
  영향: 상한이 5개면 K=7 옵션은 단일 호출 불가.
        → 분할 호출(O→wp1~5→중간점, 중간점→wp6~7→D) 설계 필요
  담당/기한: 미정

A-2. Tmap API 요금제 및 일일 호출 한도
  현황: 무료 버전 사용 중. 실험 1회당 약 900회 호출.
  확인 방법: SK open API 콘솔(https://openapi.sk.com)에서 잔여량 확인
  영향: K 옵션 검증 추가 실행 시 호출량 증가(K별 검증 시 2~3배)
        베타 운영 시 사용자 수 × 경로 요청 수만큼 호출 발생
  담당/기한: 미정

■ B. 기능 범위 결정
════════════════════════════════════════════════════════════

B-1. 핫스팟 개수 UX 옵션 도입 여부
  안: 짧게(K=3) / 보통(K=5) / 길게(K=7) 선택 제공
  현황: 코드상 K는 파라미터로 이미 열려 있어 값 변경만으로 동작
  검토 필요 사항:
    (1) 경유지 상한 확인 필요 (A-1)
    (2) BF_TOP_N=15 조정 필요 — K=7이면 대체 후보가 8개로 감소
    (3) 후보 부족 지역 대응 — 중구·서구·연수는 Buffer 후보 중앙값 6개
        K=7 요구 시 자동으로 4~5개만 경유하게 됨(k_eff=min(k,n))
    (4) K 증가 시 회피 성능 변화 미측정 — 경로가 길어지면 공단 통과
        확률 상승 예상되나 검증 안 됨
  결정 시 후속: K=5·K=7 조건 검증 노트북(v5) 실행 필요
                기존 OD 200쌍 재사용 가능, γ 스윕을 K 스윕으로 교체
  담당/기한: 미정

B-2. hard case 발생 시 폴백 정책
  현황: 폴백 미구현. 교차가 남아도 핫스팟 3개 경유 경로를 그대로 반환.
        Tmap 호출 자체 실패 시 경로 없음(final_polyline=None)
  선택지:
    (a) 현행 유지 + 알림만 표시 (구현 부담 최소)
    (b) 경유지 없이 O→D 직행 도보 경로로 대체 (안전 핫스팟 경유 포기)
    (c) 경유지를 2개로 줄여 재시도 (절충안, 호출 1회 추가)
  결정 필요 이유: 실험에서 hard case 67.7%, Tmap 실패 4% 발생
  담당/기한: 미정
