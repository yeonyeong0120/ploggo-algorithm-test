## 0. 요약

### 배경

Ploggo는 사용자가 출발지와 도착지를 입력하면 그 사이의 **무단투기 CCTV 핫스팟 K곳을 경유하는 플로깅 경로**를 추천하는 앱이다. 무단투기 CCTV 핫스팟은 인천시 '무단투기 단속 CCTV 설치 현황' 공공데이터 1,535곳으로, 단속 CCTV가 설치되었다는 사실 자체가 해당 지점에서 무단투기가 반복·심각하게 발생해 왔음을 뜻한다. 즉 플로깅 경로를 **정화가 시급한 오염 취약 지점**으로 유도하는 것이 알고리즘의 목적이다.

검증 과정에서 추천된 플로깅 경로가 **공업지대를 통과**하는 문제가 발견되어, 이를 회피하는 알고리즘(방법 C + swap)을 설계하고 v3부터 단계적으로 검증해 왔다.

### v6를 만든 이유

2026-08-26 코드 전수 조사에서 **검증 조건과 운영 조건이 다르다**는 사실이 확인되었다. 서버는 앱이 군구 정보를 보내지 않아 항상 인천 전체 무단투기 CCTV 핫스팟 1,535곳을 후보 대상으로 동작하는데, v3~v5는 요청 군구의 핫스팟만 걸러낸 조건에서 측정하였다. 또한 v4·v5 표본은 전량 '출발지-도착지 직선이 공업지대를 가로지르는' OD(출발지-도착지 쌍)여서 서비스 전체 관점의 수치가 아니었다.

이에 운영 조건(군구 필터 제거)에 맞추고 표본을 혼합(인접군 100쌍 + 분리군 100쌍)하여 재측정하였다.

### 핵심 결과 세 가지

**첫째, 경유하는 무단투기 CCTV 핫스팟이 적을수록 공업지대 회피 성능이 좋다.** K=2에서 hard case 75.0%, K=4에서 83.3%로 K가 커질수록 악화된다. 공업지대 통과를 완전히 제거한 건수도 12건에서 6건으로 절반이 된다. 수행계획서의 "무단투기 핫스팟 2~3곳 경유" 기준이 성능 면에서도 타당함이 확인되었다.

**둘째, 군구 필터 제거는 공업지대 회피 성능을 악화시킨다.** 후보 무단투기 CCTV 핫스팟이 2배(20.4곳 → 41.4곳)로 늘었음에도 hard case가 K별로 9.4~14.1%p 상승하였다. 운영 조건에 맞춘다는 명분과 성능 저하가 충돌하므로 재검토가 필요하다.

**셋째, 플로깅 경로 길이가 목표에 크게 미달한다.** K=2에서도 평균 플로깅 경로 거리가 4.82km로, 플로깅 보행 속도 3km/h 기준 약 96분이다. "30분 코스" 목표 대비 3배 이상이며, 30분 이내로 완주 가능한 플로깅 경로는 인접군 96쌍 중 0건이다.

## 1. 프로젝트 배경 (처음 접하는 독자용)

### 1-1. 무엇을 만드는가

Ploggo는 플로깅 앱이다. 플로깅(plogging)은 조깅하며 길에 떨어진 쓰레기를 수거하는 환경 정화 활동을 말한다. 사용자가 출발지와 도착지를 입력하면 그 사이를 잇는 도보 경로를 추천하되, **단순 최단 경로가 아니라 쓰레기 무단투기가 빈번한 오염 취약 지점을 경유하도록** 플로깅 경로를 구성한다.

여기서 오염 취약 지점은 **무단투기 단속 CCTV가 설치된 장소**를 의미한다. 단속 CCTV는 임의로 배치되지 않고 무단투기 민원과 적발이 반복된 곳에 설치되므로, 그 좌표는 곧 검증된 오염 취약 지점의 좌표다. 인천시 9개 군구 공공데이터에서 1,535곳(카메라 1,838대)을 수집하였으며, 본 문서에서는 이를 **무단투기 CCTV 핫스팟**(이하 CCTV 핫스팟)이라 부른다.

기존 플로깅 앱은 경로 선택을 사용자 자율에 맡겨 이미 정비된 공원·산책로에 활동이 편중되는 한계가 있었다. 본 시스템은 시민의 보행 동선을 정화가 시급한 위생 사각지대로 유도하는 것을 목표로 한다.

### 1-2. 발견된 문제 — 추천 플로깅 경로의 공업지대 통과

검증 과정에서 추천된 플로깅 경로가 **공업단지를 통과하는 경우**가 확인되었다. 공업지대는 대형 화물차가 통행하고 보행자 인도가 부족하며 공기질도 좋지 않아, 쓰레기를 주우며 천천히 걷는 플로깅 활동에 부적합하다.

이에 정부 공간정보 서비스(V-World)에서 인천시 공업지대(UQA310 전용공업 / UQA320 일반공업 / UQA330 준공업) 경계 폴리곤 147개를 수집하였다. 본 문서에서는 이 공업지대 폴리곤 집합을 **회피 영역**이라 부른다. 이로써 시스템은 어디가 공업지대인지 알게 되었으며, 남은 과제는 이를 어떻게 피할 것인가였다.

### 1-3. 설계한 해결책

두 단계로 접근하였다.

**1단계는 회피 페널티다.** CCTV 핫스팟을 선정할 때 그 핫스팟이 회피 영역(공업지대) 내부에 있으면, 오염도 점수 `S_i`가 아무리 높아도 종합 점수 `Score_i`를 크게 낮춰 선택되지 않게 한다. 점수를 깎는 강도를 조절하는 가중치가 γ(감마)다.

**2단계는 후보 교체(swap)다.** 경유할 CCTV 핫스팟 K곳을 모두 회피 영역 밖에서 선정했는데도 **그 핫스팟들을 잇는 Tmap 보행자 경로가 공업지대를 통과**하는 경우가 있다. 이때 선정된 K곳 중 하나를 다음 순위 후보로 교체하여 플로깅 경로를 재계산한다. 최대 5회까지 시도한다.

### 1-4. 주요 용어

| 용어 | 의미 |
| --- | --- |
| **무단투기 CCTV 핫스팟** (CCTV 핫스팟) | 무단투기 단속 CCTV가 설치된 오염 취약 지점. 플로깅 경로가 경유하는 대상. 인천 전체 1,535곳 |
| **`S_i` (오염도 점수)** | `cctv_count + 0.5 × neighbor_200m`. 해당 지점 카메라 대수와 반경 200m 내 인접 CCTV 핫스팟 수로 산출하는 **무단투기 심각도 지표**. 안전도와 무관 |
| **`D_i` (우회 거리)** | 해당 CCTV 핫스팟을 경유함으로써 추가되는 우회 거리 |
| **`Score_i`** | `α × S_i − β × D_i − γ × avoid_penalty_i`. 경유 핫스팟 선정 기준 점수 |
| **K** | 플로깅 경로가 경유하는 CCTV 핫스팟 개수. 현재 기본값 3 |
| **회피 영역 (공업지대)** | 인천시 공업지대 폴리곤 147개. 플로깅 경로가 통과하지 않아야 하는 구역 |
| **교차 (통과 거리)** | 추천된 플로깅 경로가 회피 영역 내부를 지나간 거리(m) |
| **hard case** | 후보 교체(swap)를 최대 5회 시도했는데도 플로깅 경로의 공업지대 통과가 해소되지 않은 경우 |
| **OD** | 출발지(Origin)-도착지(Destination) 쌍. 사용자 요청 1건에 해당 |
| **인접군 / 분리군** | 출발지-도착지 **직선**이 공업지대를 통과하는 OD / 통과하지 않는 OD |
| **Buffer 후보** | 출발지-도착지를 잇는 타원 회랑 안에 든 CCTV 핫스팟. 경유 지점 선정의 모집단 |
| **원본 플로깅 경로** | 회피 알고리즘을 적용하지 않은 상태의 추천 결과. 비교 기준선 |

## 2. v6 이전의 검증 경위

### 2-1. v3 (260727) — 회피 페널티 가중치 γ 튜닝

무작위 OD 100쌍으로 γ를 0.5·1.0·2.0·5.0으로 바꿔가며 측정하였다.

**결론: γ는 조정 효과가 없다.** γ를 10배 변경했음에도 인접군 48쌍 중 41쌍(85%)의 결과가 완전히 동일하였고, 공업지대 통과 거리 총 감소율의 차이는 2.6%p에 그쳤다. 원인은 회피 영역 내부 CCTV 핫스팟에 부여되는 `avoid_penalty_i`가 999로 극단적이어서, γ 값과 무관하게 어차피 선정에서 배제되기 때문이다. γ=1.0으로 확정하였다.

동시에 hard case 70.8%가 관측되었다.

### 2-2. v4 (260729·260731) — 표본 현실화

v3의 hard case 70.8%를 분석한 결과 **시험 표본 자체에 문제**가 있었다. 회피 영역 폴리곤의 중심을 기준으로 OD를 생성한 탓에 출발지와 도착지가 모두 공업지대 내부에 위치하는 경우가 많았고, 원본 플로깅 경로의 30.9%(중앙값)가 공업지대 내부를 통과하였다. 출발지가 공업지대 한복판이면 통과 거리 0은 원리적으로 불가능하다.

이에 출발지·도착지를 모든 폴리곤 외부에 배치하고 두 지점을 잇는 직선만 폴리곤을 통과하도록 강제한 '현실적 인접군' 표본 200쌍으로 재측정하였다.

**결론: 표본을 현실화해도 hard case는 67.7%로 거의 같았다.** 이는 문제의 원인이 표본 설계가 아니라 **도로 네트워크 제약**임을 의미한다. Buffer 후보 CCTV 핫스팟 19.4곳 중 회피 영역 내부에 있는 것은 1.94곳(10%)에 불과하여, 핫스팟 선정 단계는 이미 정상 작동하고 있었다. 문제는 **선정된 CCTV 핫스팟들을 연결하는 도보 도로가 공업지대를 관통**한다는 데 있었다.

부수적으로 유용한 사전 예측 지표를 확보하였다. 출발지-도착지 직선이 공업지대를 가로지르는 길이(chord)가 클수록 hard case 확률이 단조 증가하며, 2km 초과 구간에서는 95%였다.

이 과정에서 남동구 폴리곤이 동구로 오분류되는 버그(`'동구'`가 `'남동구'`의 부분 문자열)를 발견하여 260731 판에서 수정하였다.

### 2-3. v5 (260821~260826) — 경유 핫스팟 개수 K 스윕

UX 옵션("짧게/보통/길게 플로깅")을 검토하기 위해 경유 CCTV 핫스팟 개수 K를 2·3·4·5로 바꿔 측정하였다. 사전에 Tmap 보행자 경로 API의 경유지 상한이 5개임을 실측으로 확인하였다(6개 이상은 HTTP 400).

**결론: K=2가 모든 회피 지표에서 최선이었다.** hard case 65.6%(최저), 공업지대 통과 거리 총 감소율 25.3%(최고), 통과 완전 제거 39건(최다), 후보 CCTV 핫스팟 부족 0쌍이다. K=5는 hard case 72.4%로 가장 나빴고 후보 부족도 8.9%였다.

## 3. v6를 만든 직접적 계기

### 3-1. 코드 전수 조사 (2026-08-26)

트랙 B(서버 이식)를 앞두고 플로깅 경로 추천 파이프라인의 실패 케이스를 전수 조사하였다. 서버 5개 파일과 앱 3개 파일을 대상으로 56건의 실패 케이스를 식별하였으며, 그중 **검증 결과의 유효성에 직접 영향을 주는 항목**이 발견되었다.

### 3-2. 문제 1 — 군구 판정 단계가 운영에서 실행되지 않는다 (F-12)

노트북 검증에서는 OD가 계양구에 있으면 계양구의 CCTV 핫스팟 292곳만 대상으로 Buffer 후보를 추출하였다. 서버 코드도 같은 구조로 작성되어 있다.

```python
subset if len(subset) > 0 else hotspots   # algorithm.py:460-461
```

그러나 **앱이 `district`(군구) 값을 서버에 보내지 않는다.** 따라서 `subset`이 비어 항상 폴백이 발동하고, 인천 전체 CCTV 핫스팟 1,535곳이 후보 대상이 된다. 강화군에만 적용되는 Buffer 반경 2.5km 규칙도 작동하지 않는다.

즉 측정한 조건과 실제로 돌아가는 조건이 달랐다.

**결정: 군구 필터 제거.** 행정 경계 건너편의 CCTV 핫스팟을 배제하는 것이 부자연스럽고, 1,535곳 계산은 haversine 3회와 벡터 연산이므로 밀리초 단위여서 성능 부담이 없다는 판단이었다. 다만 이 결정에 따라 재검증이 필요해졌다.

### 3-3. 문제 2 — 시험 표본이 편중되어 있다

v4·v5 표본 200쌍은 전량 인접군이어서 원본 플로깅 경로의 공업지대 통과 발생률이 86%였다. 이는 **공업지대를 가로지르는 요청에 한정한 값**이며 서비스 전체 관점의 수치가 아니다. 실제 사용자 요청 중 공업지대를 가로지르는 비율은 훨씬 낮을 것이다.

최종 검증이므로 분리군을 추가하여 인접군 100쌍 + 분리군 100쌍으로 구성하기로 하였다.

### 4-2. 표본 구성

인접군 100쌍은 v4(260731) 표본 200쌍에서 앞에서부터 취하여 군구 균등 배분을 유지하였다. 단 Buffer 후보는 인천 전체 CCTV 핫스팟을 대상으로 재계산하였다. 분리군 100쌍은 신규 생성하되, 출발지·도착지가 회피 영역 밖이면서 출발지-도착지 직선이 회피 영역에서 500m 이상 떨어질 것을 요구하였다.

생성 후 자동 검증에서 조건 위반 0건이 확인되었다. 군구 분포도 인접군·분리군 각각 11~12쌍씩 균등하다.

### 4-3. 실행 방식

Tmap 무료 호출 한도를 고려하여 K별로 하루 1회씩 나누어 실행하였다. 배치별 checkpoint를 저장하여 중단 시 재개 가능하도록 하였고, K별 하위 폴더로 분리하여 덮어쓰기를 방지하였다.

## 6. 분석

### 6-1. 경유 핫스팟이 많을수록 나빠지는 이유

경유하는 CCTV 핫스팟이 늘어나면 플로깅 경로가 길어지고 굴곡이 많아져 공업지대를 지날 기회 자체가 증가한다. K=2에서 4.82km이던 플로깅 경로가 K=4에서 6.34km로 1.5km 늘어난다.

동시에 후보 교체(swap)의 실효성이 떨어진다. 평균 swap 횟수는 K=2에서 3.60회, K=4에서 3.38회로 오히려 감소하는데, 이는 교체 여지가 줄었다기보다 **교체해도 개선되지 않아 조기에 최선값이 고정되는** 것으로 해석된다.

### 6-2. 군구 필터 제거가 악화를 유발한 이유 (추정)

코드 조사에서 식별된 F-40 항목과 연결된다. swap은 공업지대 통과 발생 시 `avoid_penalty_i`가 가장 큰 CCTV 핫스팟을 교체하는데, 이 페널티는 출발지-핫스팟-도착지를 잇는 **직선** 기준으로 계산된다. 직선상으로는 회피 영역을 지나지 않으나 실제 Tmap 보행자 경로는 통과하는 경우, 선정된 핫스팟들의 페널티가 모두 0이 되어 교체 대상 선택이 사실상 무작위가 된다.

이 상황에서 후보 CCTV 핫스팟이 2배로 늘면 **잘못된 조합에 빠질 확률만 증가**한다. 실제로 Buffer 후보 중 회피 영역 내부에 있는 핫스팟은 평균 3.81곳으로, 전체 41.4곳의 9%에 불과하다. 나머지 91%는 페널티가 0이어서 교체 판단 근거가 없다.

따라서 필터 제거로 인한 악화가 필터 자체의 문제인지, swap의 방향성 부재가 후보 증가로 증폭된 것인지는 현재 데이터로 구분되지 않는다.

### 6-3. 플로깅 경로 길이 문제의 구조

플로깅 경로가 길어지는 원인은 Buffer 후보 추출 조건에 있다. `filter_candidates_by_ellipse_buffer`는 다음 조건을 만족하는 CCTV 핫스팟을 후보로 받아들인다.

```
d(O, h) + d(h, D) - d(O, D) < buffer_r × 1.5
```

즉 CCTV 핫스팟 하나가 유발하는 우회 초과분이 2.25km(1.5km × 1.5) 이내면 허용된다. K=2면 이론적으로 4.5km까지 늘어날 수 있으며, 여기에 실제 도로를 따라가는 가산분이 더해진다.

v4 분석에서 출발지-도착지 직선거리가 1.2km인 경우에도 플로깅 경로 거리가 4.17km로 나타났다. 출발지와 도착지를 가깝게 설정하는 것만으로는 플로깅 경로가 짧아지지 않는다.

### 6-4. K=5를 측정하지 않아도 되는 근거

K=2·3·4에서 hard case가 75.0 → 80.2 → 83.3%로 단조 증가하며, v5(군구 필터 적용 조건)에서도 65.6 → 67.7 → 69.3 → 72.4%로 같은 방향이었다. K=5에서 85% 안팎이 예상되며, "경유 CCTV 핫스팟은 적을수록 낫다"는 결론은 바뀌지 않는다.

## 7. 결론 및 후속 과제

### 7-1. 확정 가능한 결론

**경유 CCTV 핫스팟 개수 K는 2~3 범위가 적절하다.** K=2가 모든 회피 지표에서 최선이며, 이는 v5(군구 필터 적용)와 v6(필터 제거) 두 조건에서 일관된다. 수행계획서의 "무단투기 핫스팟 2~3곳 경유" 기술과도 부합한다. K=4 이상은 hard case가 8%p 이상 상승하고 통과 완전 제거가 절반으로 줄어 회피 성능을 뚜렷이 희생한다.

**분리군에 대한 부작용은 없다.** 후보 CCTV 핫스팟 확대와 회피 페널티가 공업지대와 무관한 플로깅 경로에 영향을 주지 않음이 재확인되었다.

### 7-2. 재검토가 필요한 사항

**군구 필터 제거 결정.** 운영 조건에 맞춘다는 명분으로 결정하였으나, 실측 결과 hard case가 9~14%p 상승하였다. 세 가지 선택지가 있다.

첫째, 앱이 `district`(군구)를 전송하도록 수정하여 기존 검증 조건을 복원한다. v3~v5 결과가 그대로 유효해진다.

둘째, 인접 군구까지 포함하는 절충안을 적용한다. 후보 CCTV 핫스팟 풀을 적당히 유지하면서 지나치게 먼 핫스팟을 배제한다. 별도 검증이 필요하다.

셋째, swap 로직(F-40)을 개선한 뒤 재판단한다. 악화 원인이 swap의 방향성 부재라면, 개선 시 후보가 많은 것이 오히려 유리해질 수 있다.

**플로깅 경로 길이 상한.** 현재 알고리즘은 CCTV 핫스팟 선정에만 집중하고 총 이동 거리 제약이 없어 K=2에서도 평균 4.82km(약 96분)이다. "30분 코스" 목표와 3배 이상 차이가 나므로, Buffer 임계값 조정 또는 총 거리 상한 도입이 필요하다.

### 7-3. 미완료 항목

K=5 측정과 K=4의 분리군 2배치가 Tmap API 한도 소진으로 미완료 상태이다. 인접군 결론에는 영향이 없으나, 전체(서비스 관점) 수치를 K=4까지 확장하려면 보완이 필요하다.

Tmap 무료 사용량 체계(일 단위 / 월 단위)와 잔여량 확인이 선행되어야 한다.

## 부록. 비전문가 대상 요약

### 무엇을 확인하려 했는가

Ploggo는 사용자를 **쓰레기 무단투기가 잦은 지점**으로 유도하는 플로깅 앱이다. 무단투기 단속 CCTV가 설치된 곳은 그만큼 무단투기가 반복된 곳이므로, 그 좌표 1,535곳을 경유 대상(CCTV 핫스팟)으로 사용한다.

그런데 이렇게 만든 플로깅 경로가 **공업단지를 지나가는** 경우가 있었다. 화물차가 많고 인도가 부족해 쓰레기를 주우며 걷기에 부적합하다. 이를 피하는 기능을 만들었고, 그것이 실제로 작동하는지 확인해 왔다.

이번 검증에서는 두 가지를 바꾸어 다시 측정하였다. 하나는 **실제 서버가 동작하는 방식에 맞춘 것**이고, 다른 하나는 **시험 문제를 현실에 가깝게 섞은 것**이다.

### 서버 동작 방식을 왜 맞췄나

지금까지의 시험은 "계양구 요청이면 계양구의 CCTV 핫스팟만 검토"하는 방식이었다. 그런데 실제 서버는 앱에서 지역(군구) 정보를 받지 못해 **인천 전체 CCTV 핫스팟 1,535곳을 매번 검토**하고 있었다. 시험 조건과 실제가 달랐던 것이다.

행정 구역 경계 바로 건너편에 있는 무단투기 지점을 굳이 제외할 이유가 없으므로, 실제 방식에 맞추기로 하고 다시 측정하였다.

### 시험 문제를 왜 섞었나

이전 시험은 200개 OD가 **전부 공업지대를 가로지르는** 조건이었다. 어려운 문제만 모아 놓은 셈이라, 실제 사용자가 겪을 상황과는 거리가 있었다. 이번에는 공업지대를 지나는 OD 100개와 공업지대와 무관한 OD 100개를 절반씩 섞었다.

### 결과 — 세 가지

**첫째, 경유하는 CCTV 핫스팟은 적을수록 좋다.** 2곳을 경유할 때 회피 실패율 75%, 4곳을 경유할 때 83%로 나빠진다. 공업지대 통과를 완전히 없앤 경우도 12건에서 6건으로 절반이 된다. 많은 지점을 경유할수록 플로깅 경로가 길고 복잡해져 공업지대를 만날 기회가 늘기 때문이다.

**둘째, 검토 대상 CCTV 핫스팟을 늘렸더니 오히려 나빠졌다.** 후보가 2배(20곳 → 41곳)로 늘었는데 회피 실패율이 9~14%p 올랐다. 선택지가 많아지면 좋을 것 같지만, 현재 알고리즘은 어느 핫스팟을 교체해야 할지 판단하는 기준이 약해서 선택지가 많을수록 헤매는 것으로 보인다. 이 부분은 알고리즘 개선 과제로 남았다.

**셋째, 플로깅 경로가 너무 길다.** 가장 짧은 조건(2곳 경유)에서도 평균 4.8km이다. 쓰레기를 주우며 걷는 속도(시속 3km)로 환산하면 약 1시간 36분이며, **30분 안에 끝나는 플로깅 경로는 96개 중 하나도 없었다.** 목표로 하던 "짧은 플로깅 30분"과 큰 차이가 있어, 플로깅 경로 길이를 제한하는 장치가 필요하다.

### 앞으로 할 일

경유하는 CCTV 핫스팟 개수는 2~3곳으로 정하면 된다는 결론이 나왔다. 남은 과제는 두 가지다.

하나는 **군구 필터를 어떻게 할지 다시 정하는 것**이다. 실제 서버 방식에 맞췄더니 성능이 떨어졌으므로, 앱이 군구 정보를 보내게 하거나 인접 군구까지만 포함하는 절충안을 검토한다.

다른 하나는 **플로깅 경로 길이를 제한하는 것**이다. 현재는 CCTV 핫스팟을 고르는 데만 집중하고 총 이동 거리를 따지지 않는다. 사용자가 원하는 시간에 맞는 플로깅 경로가 나오도록 상한을 두어야 한다.
